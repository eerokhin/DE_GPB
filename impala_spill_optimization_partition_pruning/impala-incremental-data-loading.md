# Оптимизация тяжёлых запросов в Impala: CREATE TABLE + последовательные INSERT INTO

## 1. Проблема

При обработке большого объёма данных один SQL-запрос может потреблять слишком много памяти и вызывать **spill** — запись промежуточных данных на диск, когда операция не помещается в доступную память.

Например, необходимо сделать `JOIN` двух больших таблиц (Таблицу 1 - с атрибутами 1,2 приоритета; и Таблицу 2 с атрибутами 3,4 приоритета).

Один из вариантов — разбить запрос на двухлетние интервалы и объединить их через `UNION ALL`. Однако все ветки остаются частью одного SQL-запроса, а потребление ресурсов зависит от плана выполнения Impala.

## 2. Идея оптимизации

Вместо одного большого запроса можно:

1. Создать целевую таблицу с помощью `CREATE TABLE`.
2. Последовательно загружать данные за отдельные периоды с помощью `INSERT INTO`.
3. После завершения загрузки проверить результат.

Таким образом, каждый самостоятельный запрос обрабатывает только свой диапазон дат.

## 3. Реализация

### Шаг 1. Создание целевой таблицы

Например, можно создать пустую таблицу на основе структуры исходной таблицы:

```sql
DROP TABLE IF EXISTS sbx_041.result_table
/
CREATE TABLE IF NOT EXISTS sbx_041.result_table(
                                                user_id INT COMMENT 'Пользователь',
                                                object_id INT COMMENT 'Объект',
                                                week_num INT COMMENT 'Номер недели',
                                                ..................
                                                )
PARTITIONED BY (report_dt DATE COMMENT 'отчетная дата')
COMMENT 'Джоин таблиц витрин агрегатов - 1-й, 2-й приоритет с 3-м, 4-м приоритетом'
STORED AS PARQUET
```

### Шаг 2. Загрузка данных за 2021–2022 годы

```sql
INSERT INTO TABLE sbx_041.result_table
PARTITION (report_dt)
SELECT a.user_id,
       a.object_id,
       a.week_num,
       ......необходимые атрибуты,
       c.какойто_атрибут,
       CAST(a.report_dt AS DATE) AS report_dt
FROM sbx_041.ees_input_contact_interact_1_tmp a
LEFT JOIN sbx_041.ees_only_5_priority_4_tmp c
ON a.user_id = c.user_id AND a.object_id = c.object_id AND a.report_dt = c.report_dt
WHERE a.report_dt >= '2021-01-01' AND a.report_dt <  '2023-01-01';
```

### Шаг 3. Загрузка данных за 2023–2024 годы

```sql
INSERT INTO TABLE sbx_041.result_table
PARTITION (report_dt)
SELECT a.user_id,
       a.object_id,
       a.week_num,
       ......необходимые атрибуты,
       c.какойто_атрибут,
       CAST(a.report_dt AS DATE) AS report_dt
FROM sbx_041.ees_input_contact_interact_1_tmp a
LEFT JOIN sbx_041.ees_only_5_priority_4_tmp c
ON a.user_id = c.user_id AND a.object_id = c.object_id AND a.report_dt = c.report_dt
WHERE a.report_dt >= '2023-01-01' AND a.report_dt <  '2025-01-01';
```

Далее аналогично загружаются остальные периоды вплоть до необходимой даты.

### Шаг 4. Проверка результата

```sql
SELECT
    MIN(report_dt) AS min_report_dt,
    MAX(report_dt) AS max_report_dt,
    COUNT(*) AS row_count
FROM sbx_041.result_table;
```

Запрос позволяет проверить диапазон дат и общее количество записей.

## 4. Почему это может помочь

**Основная цель — уменьшить пиковое потребление памяти при обработке данных.**

- Каждый запрос обрабатывает ограниченный диапазон дат.
- Для одного запуска может потребоваться меньше памяти.
- Если spill связан с большим объёмом данных в конкретной операции, уменьшение входного объёма может снизить вероятность spill.
- При ошибке можно повторно обработать отдельный период.

Однако результат зависит от плана выполнения, партиционирования и характера spill. Уменьшение периода не гарантирует, что проблема исчезнет.

## 5. Сравнение подходов

| Критерий | `UNION ALL` | Последовательные `INSERT INTO` |
|---|---|---|
| Выполнение | Один большой SQL-запрос | Несколько самостоятельных запросов |
| Потребление памяти | Зависит от общего плана и параллелизма | Может быть ниже на один запуск |
| Общее время | Может быть меньше | Может увеличиться из-за отдельных запусков |
| Повторная обработка периода | Нужно повторно выполнять соответствующую логику | Можно перезапустить отдельный период |

## 6. Важные нюансы

### Повторная загрузка

`INSERT INTO` дописывает данные, а не заменяет ранее записанные строки. Повторный запуск того же периода может привести к дубликатам.

Перед повторной загрузкой необходимо предусмотреть очистку соответствующего периода, замену партиции или другой безопасный механизм перезапуска.

То есть перед каждой сборкой витрины, промежуточная таблица с расчетами sbx_041.result_table должна всегда очищаться. Должен быть заранее подготовлен какой то механизм инкрементальной загрузки.

### Партиционирование

Если таблица партиционирована по `report_dt`, стоит проверить, насколько эффективно Impala отбирает нужные партиции. Для больших таблиц это может существенно влиять на объём чтения.

### Схема целевой таблицы

Количество столбцов, их типы и порядок в `SELECT` должны соответствовать целевой таблице. Если используются атрибуты из обеих таблиц, схема должна включать все необходимые столбцы.

## 7. Как проверить эффективность

Сравнить оба подхода на одинаковом диапазоне дат и одинаковых исходных данных.

Проверить:

- время выполнения;
- наличие и объём spill;
- пиковое потребление памяти;
- объём прочитанных данных;
- количество обработанных строк.

Для анализа плана выполнения использовать `EXPLAIN` и `PROFILE` в Impala.

## Вывод

Последовательные `INSERT INTO` позволяют разделить обработку большого исторического периода на несколько самостоятельных запросов.

Если единый запрос вызывает spill, а обработка отдельных периодов проходит успешно, такой подход может уменьшить пиковое потребление памяти и повысить надёжность загрузки.

**Ключевой принцип:** сначала создать целевую таблицу, затем загружать данные отдельными периодами и обязательно предусмотреть безопасный повторный запуск.
